## 2 Introduction 

Machine Readable Travel Documents (MRTDs) usually feature a standardized Machine Readable Zone (MRZ) with biographic data and an electronic chip. In addition to typical textual areas on MRTDs, many documents also feature special optical/physical properties which can only be recognized and evaluated by special record ing equipment. These properties are intended as an additional indicator for the authenticity of a document or they can be used for establishing a link between the document and its owner. Besides these features, the inte grated chip contains information that is printed on the document, e. g. name, date of birth, but also biometric characteristics and cryptographic material that ensures that a given document was issued by an official entity and was not altered, cloned or forged. 

This Technical Guideline (TR) defines requirements for document inspection using document inspection sys tems and a normative description of the necessary procedures that are required for an exhaustive check of (electronic) machine readable identity and travel documents, to acknowledge that a checked MRTD is au thentic, of integrity, and valid. 

The German Federal Office for Information Security (Bundesamt für Sicherheit in der Informationstechnik (BSI)) composed [BSI TR-03135] (TR : Technische Richtlinie, German for Technical Guideline) in collaboration with the Federal Criminal Police Office (Bundeskriminalamt (BKA)), the Federal Police (Bundespolizei (BPOL)), and the Federal Office of Administration (Bundesverwaltungsamt (BVA)). 

## 2.1 Structure of this Technical Guideline 

This Technical Guideline consists of the following parts: 

- Part 1: Overview and Functional Requirements (TR-03135-1) 

This part describes the process and protocols for reading Electronic Machine Readable Travel Documents (eMRTDs). It outlines the optical, electronic, and combined checks used to ascertain the authenticity, inte grity, and validity of such documents. It also provides instructions and procedures for handling of defects which may occur during an inspection process. Furthermore, it specifies a logging scheme for recording the technical activities and results of an inspection process. 

- Part 2: Application profiles for official document inspection systems (TR-03135-2) 

This part describes the operational scenarios for document inspection systems in public sector applications, as well as the corresponding requirements regarding document checks and operational monitoring. 

- Part 3: High Level Document Check Interface Specification (TR-03135-3) 

This part describes a client-server architecture for document checks. It specifies interfaces for document checks controlled by workflow definitions and transaction-based logging of the results.

## 3 Overview 

This chapter describes the basic architecture of document inspection environments. Requirements for the document readers are described in Chapter 4, while the coverage of such checks are specified in Chapter 5. Chapter 6 specifies the contents and the logging format of the document checking process. Conformance requirements are described in Chapter 7. 

It is recommended to have a look into “Machine Readable Travel Documents” [ICAO9303] and “Best Practice Operational Guidelines for Automated Border Control (ABC) Systems” [FRONTEX]. For Identity Documents the Technical Guidelines [BSI TR-03127] and [BSI TR-03110] are recommended as additional reading. 

## 3.1 Document components 

This TR views an MRTD as a set of several components. The types of components are as follows: 

- Optical component (see Section 3.1.1), 

- Electronic component (see Section 3.1.2), 

- Digital seal component (see Section 3.1.3). 

Each component consists of several features, which can be processed by machines. The features are recor ded by a document reader component (see Section 3.3) and processed in an Inspection Application (see Section 3.4). Internationally formalized and standardized document features of MRTDs are specified in [ICAO9303]. In addition to standardized features, many documents also contain specific information and fea tures which can be used as an indicator for the authenticity and integrity of a specific MRTD. MRTD features can be catalogued, so software can rely on such information to perform a complete and reliable document authentication. 

However, not all features of a MRTD have to be checked or can be checked. The scope of the check is depen dent on the application scenario (see [BSI TR-03135-2]), the MRTD type and the Inspection System (IS) (see Section 3.5) used to read and analyse the features. It is RECOMMENDED to specify mandatory checks in a profiling document with respect to this Technical Guideline. 

## 3.1.1 Optical component 

In general, the document under inspection is a physical document with pages that can be checked optically. These contain printed data regarding the holder and issuer of the document. The most prominent way to transport information for computer assisted processing is by encoding these inside a machine-readable string, the MRZ, which can be read using Optical Character Recognition (OCR). Besides, information that is human readable is printed on the document as well. In principle, this information can be read automatically, however, this process is more prone to errors since no special font is used and there are no check numbers. Printed documents are protected by using special optical patterns, paper and dyes and printing techniques to prevent tampering. In the context of this TR, an optical component encompasses all the document pages required for an inspection. 

## 3.1.2 Electronic components 

More advanced documents, such as passports, can contain a chip that stores information which is cryptogra phically protected against modification and against physical tampering. Additionally, access to the informa tion as well as the reading process can be protected. Besides on chips, information can also be stored on other authenticators, such as smart devices, in case of Digital Travel Credentials (DTCs). In both cases, chip and DTCs, are regarded as electronic components of a document. 

## 3.1.3 Digital seal components 

Barcodes or multi-dimensional matrix codes are methods to encode information in a machine readable for mat. They can also be used to protect the information contained against tampering. Though, in general, less information can be stored when compared to electronic components (e.g. chips). A document can encompass several digital seal components. Each of them can be checked as part of a document check.

## 3.1.4 Checking components 

Inspecting a document means checking its components. Besides individual checks, this TR defines checks bet ween the components. These combined checks are used to compare the information and check for plausibility. 

Depending on the checking process, more than one document needs to be processed in an inspection. In these cases, the documents are linked and need be cross checked for plausibility. Here, this is the case for visas. 

In the following sections, the document checks of an individual document as well as checks across documents are the subject of discussion. 

## 3.2 MRTD features 

This Technical Guideline assumes that MRTDs are equipped with a combination of 

- optical/physical and 

- electronic (digital) 

features, which can be processed by machines. These are recorded by some kind of document reader and pro cessed in an Inspection Application. Internationally formalized and standardized document features are spe cified in [ICAO9303] for MRTDs. In addition to standardized features, many documents also contain specific information and features which can also be used as an indicator for the authenticity and integrity of a specific MRTD. They can be catalogued, so software can rely on such information to perform a complete and reliable document authentication. 

Not all features of a document have to be checked or can be checked. The scope of the check is dependent on the application scenario, the document type and the equipment used to read and analyse the features. It is RECOMMENDED to specify mandatory checks in a profiling document with respect to this Technical Guideline. 

## 3.3 Document reader component 

The document reader component, also called document reader, records the features of a given MRTD accord ing to its type. It transmits the collected records to an Inspection Application for further processing. 

## 3.4 Inspection Application 

In this Technical Guideline, the Inspection Application controls the reading process of the document reader (component) and processes the information obtained from a MRTD depending on the profile and the type of document. The Inspection Application is able to configure the document reader (component) according to the operational requirements and type of the document to read. It actively monitors and controls the steps needed to exhaustively read and process a given travel document and its features. 

## 3.5 Inspection System 

The Inspection System comprises of the Inspection Application, the document reader component and all background information systems involved in the execution of a document check. 

## 3.6 Authentication processes and their result 

In the context of this Technical Guideline the main focus is to determine if a given travel document is 

- authentic (i. e. genuine, originating from the issuer) 

- of integrity (without any manipulation) and 

- valid (e. g. not expired, not reported as lost or stolen, not a fantasy document) 

These checks can be applied to the entire document or just partial areas of the MRTD and refer to the docu ment's components and their features. An individual check consists of a well-defined checking process. Ex amples for checking processes are:

- Check if a given document's optical component can be read in near-infrared light (infrared (IR)) wavelength range ~900 nm. 

- Check if there are defined patterns of an optical component that become visible or invisible under exposure by a certain light source. 

- Check the validity of a document (e. g. via an optical component's MRZ's date of expiry). 

- Perform a query to background systems regarding the data of an optical component's MRZ to determine if the document is marked as lost or stolen. 

- Calculate the checksums of the data groups read from an electronic component to confirm its integrity. 

- Check the digitally signed checksum an electronic component or digital seal component to prove integrity. 

- Do a plausibility cross-check between information for an optical component (e. g. MRZ on a page) and the corresponding information from an electronic component (e. g. `EF.DG1` in the chip). 

An individual checking process SHALL always lead to a well-defined and verifiable result. As such, an indivi dual checking process is either 

**processed completely** according to its algorithm until it is terminated and delivers a well-defined check result 

or 

**aborted** ahead of schedule and does not deliver a meaningful check result. 

The amount of checking processes performed depends on the application scenario defined by the profiling and the work-units specified therein which are prescribed as a complete check. 

At the end of the checking processes, all individual checks are assorted to intermediate results and an overall check result for each category to build a final assessment. 

## 3.6.1 The MRTD Checking Process 

Within this document, the organized and oriented sequence of a check is formally defined as a checking pro cess. This sequence defines what is to be recorded, measured and controlled as part of its check and which results a process can return. 

Remark: In this Technical Guideline, the checking process is just a formally variable and does not define how a check is technically implemented in hard- or software. The description of the technical design and imple mentation of a checking process, its in- and output values are out of scope. 

A checking process P formally describes the sequence of causal dependence state transitions at times t1, ..., ti ti+1 , ...., tE , i. e. the sequence of the checking events from the start t1 to the end tE. Here, a checking process is a series of deterministic state transitions Zi → Zi+1 from state Zi to state Zi+1, whereas each state depends on previous states and is explicitly derived by them. 

A checking process can only be in one of the following global states: 

1. **Initiated** 

The checking process has not started yet, there has been no activity. The process is in the state Z{} , the so called idle state. 

2. **Running** 

At time i, the checking process is in the state Zi and is being performed at this time. 

## 3. **Terminated** 

The checking process was performed until the deterministic end (time E) of its life cycle with final state ZE having been reached. It delivers a sound result that can be used to rate a given document and its checked feature(s). 

## 4. **Aborted**

The checking process was aborted prior to its defined end at time X of the life cycle with state ZX. The che cking process was not able to finish correctly and thus does not deliver a complete result[1] . It is RECOM MENDED that an error code and a short description is provided. 

The result of a process terminated at time E and state ZE SHALL be used for determining the authenticity, integrity and validity. Errors during the operation, hardware, software or handling errors can cause a prema ture abortion of the process in a state ZX at time X (i.e. aborted). In order to ensure constant checking quality, only check results arising from a terminated process (terminated at time E and state ZE) SHALL be used as a check result. The information of any other state (notably state aborted) MAY only be documented and used in some kind of operational monitoring; these values, however, SHALL NOT form a basis for any reasonable check result. 

Only the result of a terminated process (terminated at time E and state ZE) SHALL be input for another basic checking process or any final result. 

## 3.6.2 Check results 

The result of a checking process has exactly one of the following results: 

- `successful` 

The check **terminated** , the feature of the document to be checked successfully passed the check, i.e. a spe cific check was able to be applied to the document and assessed according to its specifications 

- `failed` 

The check **terminated** , the feature of the document to be checked did not successfully pass the check; in other words, the applied check failed on the feature. The document SHOULD be subject to a further (ma nual) check for authenticity, integrity and validity 

- `undetermined` 

The check **terminated** , it was not possible to determine if the feature to be checked is authentic, of integrity or is valid. The document SHOULD be subject to a further (manual) check. 

- `not supported` 

The check **terminated** , but the specific document does not support the features to be checked (for example, a document without a chip, a document which does not have specific security features per definition, a specific protocol was not supported by a chip etc.) 

The final result SHALL be given according to one of the values prescribed above. Besides the check result, further information MAY also be attached. The result can then be used together with its attached information in further checks. 

Otherwise the check must be **aborted** and there is no meaningful result with regard to the intended document check. In those cases, the following check result shall be used: 

- `aborted` 

The check aborted prior to its defined process flow. Obtained check information and results SHOULD NOT be used as proper document check indications. 

## 3.7 Different types of checks 

Checks on MRTDs can be divided into several categories, which are: 

- Optical checks: These checks concern an optical component. 

- Electronic checks: These checks concern an electronic component.

- Digital seal checks: These checks concern a digital seal component. 

- Combined checks: These checks concern multiple components (e.g. comparing an optical component's MRZ data with an electronic component's MRZ data). 

- Cross document checks: Theses checks concern separate related documents (e.g. a passport and a visa for the same person). 

Typically, further checks are subsequently performed, for example: 

- Biometric checks: Checking the identity of the document owner based on biometric characteristics (e. g. facial image, fingerprint images) initially recorded when the official document was applied for. These are checked against the live data collected on site to verify that the current document holder is the one the document was issued for. 

- Requests into background systems: Automated requests to background information systems on the basis of the information featured on an MRTD (e. g. searching with MRZ data in official databases like INPOL, SIS, VIS, RTP, etc.). 

Although the document owner's identity will be determined in a complete checking process, this Technical Guideline focuses on checking the document itself. The relation between the owner of an MRTD and the document itself is often established by comparing biometric characteristics (the facial image or fingerprints) to the characteristics stored in the electronic chip of the eMRTD. Checking the biometric characteristics can also be performed manually or by using automated systems. More details and requirements for such checks and logging formats are defined in [BSI TR-03121] and are not part of this TR. 

## 3.8 Operational profiling 

This Technical Guideline contains a number of checks that could be performed on MRTDs. The requirements on how and what to check depends on the application scenario and SHOULD be specified by the agency res ponsible for checking MRTDs. As such, all necessary checks and requirements SHOULD be defined in a pro filing document[2] referencing this Technical Guideline. Any restrictions, deviations and specific designs of the checks which were not implemented in accordance herein SHALL be concretized accordingly in the profiling. 

Document checks as defined in this Technical Guideline can be: 

- **Mandatory (m)** i.e. SHALL always be performed and SHALL be included in the final result. 

- **Conditionally Ignored (c)** i.e. SHALL always be performed and SHALL be included in the final result, unless certain conditions are met. 

- **Optional (o)** i.e MAY be implemented and performed. If they are implemented in a checking process, the results of the checks SHALL be included in the final result. 

- **Evaluatory (e)** i.e. SHALL NOT be included in the final result and are only documented in the log for sub sequent evaluations and operational monitoring. 

Depending on the requirement and the profiling, all data obtained during an authentication process SHALL be stored according to the monitoring log-data format. Further information and details on this can be found in Chapter 6.

## 4 Inspection System Requirements 

## 4.1 Reader requirements 

## 4.1.1 Document formats 

A full-page MRTD document reader SHALL support the sizes and formats for MRTDs specified in [ICAO9303]. This includes documents in the sizes TD-1, TD-2 and TD-3 as well as machine-readable visas in the MRV-A and MRV-B formats[1] . 

## 4.1.2 Reading the MRZ/CAN 

The document reader SHALL support automated reading of the MRZ according to the definition in [ICAO9303]. If it is a full-page reader, it SHALL be able to record the image in the near-infrared light (B900 band, 900 +/- 50 nm) and SHOULD be able to read images in the visible wavelength range. More detailed in formation can be found in [ISO1831]. 

A full-page reader SHALL also support the automated reading of the six-digit Card Access Number (CAN) that can be found on some eMRTDs or IDs. 

It is RECOMMENDED that swipe-type document readers also support reading the CAN in addition to the MRZ. 

## 4.1.3 Applying and handling the document on a full-page reader 

MRTDs SHALL be placed on a full-page reader such, that the personalized data page can be recorded optically without any interference. 

The MRZ or the CAN are placed in the direction of the document reader. Figure 4.1 shows an example on how an electronic passport and an identity card SHOULD be placed on a full-page reader. In the following this will be called the end position of the document. 


![](markdown/tr/BSI-TR-03135-1-v5/BSI-TR-03135-1-v5.pdf-0016-12.png)


**Figure 4.1.** Example on how to place a passport and an ID card on a typical document reader 

The document reader can digitize the data page of an MRTD and then start further checking steps. It is RE COMMENDED that the electronic reading process should start as soon as the MRZ or the CAN is available. It is RECOMMENDED that digitized records of the extracted MRZ or CAN are available to the system in less than 5 seconds after the document is in the end position (see Section 4.1.3). 

## 4.1.4 Communication requirements for the RF-reading module 

The Radio-Frequency (RF)-reading module SHALL communicate with a semi-conductor device embedded in the eMRTD using radio frequency energy that meets the requirements specified in [ISO14443-2]. 

The document reader SHALL be able to read eMRTDs with an electrically conductive shielding. 

Reading the electronic data[2] of an eMRTD SHALL NOT take longer than 7 seconds on a reference eMRTD, using the minimal system requirements as specified by the vendor of the inspection system. The start time for measuring this requirement is the point in time when the document is in the end position (see Section 4.1.3) on the reader and all information needed to process the document (MRZ, CAN) is available to the inspection system.

## 4.1.5 Host system interface 

If the Inspection System is partitioned in several components, such as document reader, RF-reader, and In spection Application on a computing unit, the connection interfaces between the components SHOULD pre ferably be used by means of common industry standards, e. g. Universal Serial Bus (USB). 

## 4.1.6 Requirements for the optical reading component 

Images from the MRTDs data page SHALL be optically recorded and digitized under near-infrared light (in the B900 band, cf. document specification according to [ISO1831]), under ultraviolet (UV) light of a wavelength of approx. 365 nm and under white light reflecting colours of the visible spectrum in roughly equal amounts. 

Ambient light can have a significantly adverse effect on the quality of the scanned records; thus, it is RECOM MENDED to use a document reader which is insensitive to incoming ambient light or can be shielded. 

The document Inspection Application SHALL provide all records of the data page in computer readable image file formats (Portable Network Graphics (PNG) or JPEG (JPEG)) with an image resolution of at least 385 pi xels per inch (PPI)[3] , in the sense of scale mapping the sensor size to the document size. For JPEG, the ope rator SHALL be able to configure the encoding for different compression factors and quality settings, see [ISO10918-1]. 

## 4.2 Background Public Key Infrastructures Requirements 

While inspecting the electronic components and digital security features of eMRTDs standardized protocols SHALL be performed. Most of these protocols depend on Public Key Infrastructures (PKIs). These include the protocol that verifies that the data stored on the MRTDs was not altered and is trustworthy and the protocols that detect cloned chip contents. 

The PKIs used within this document are issuer PKIs according to [ICAO9303] and Extended Access Control (EAC) PKIs according to [BSI TR-03110] who are fundamental building blocks for a chain of trust regarding eMRTDs. 

In order to facilitate a complete electronic check, an Inspection System SHOULD support: 

- Implementation of Terminal Authentication (TA) (see Section 5.8.9.2) 

- Master List and Signer List handling and verification of signer certificates and Country Signing Certificate Authority (CSCA) certificates (see Section 5.6.3.2) 

- Defect Lists handling for a given Document Signer (DS) or CSCA certificate (see Section 5.12) 

- Implementation of Passive Authentication by means of the IS (see Section 5.8.4 and Section 5.8.5) 

The profiling SHALL specify what to implement and specify additional details where needed.

## 5.7.2.1 Document model 

Each MRTD can be assigned to a document model (sometimes also called document series). A document model is defined by means of the country code ( **C** ), document type ( **T** ), a distinct identification number ( **N** ), a year value ( **Y** ), a PRADO [PRADO] code identifier ( **P** ), a subdivision or state ( **S** ) and an organization ( **O** ) : 

Document Model := ( **C, T, N, Y, P, S, O** ) 

The country code **C** SHALL be a three-letter code according to [ICAO9303]. 

The first digit of the document type **T** is specified in [ICAO9303].

## 5.7.2.2 Spectrally selective checks 

The term "spectrally selective checks" covers checks, that record different reactions occurring on a document illuminated with visual ( **VI** , white light) or non-visual ( **UV** , **IR** ) illumination. Based on the three records ( **VI** , **UV** , **IR** ), the absorbent, reflective or luminescent features of these reactions can be checked. Examples for checks are the MRZ IR readability, the VIZ IR readability, the UV brightness test and sample verifications in all images. With a few exceptions these checks can only be defined for a specific model of documents. Hence a check database is required to assist the checking process. Such a database contains model-specific spectrally selective check information about known documents. The actual characteristics of a spectrally selective check routine depend on the vendor of the inspection system. 

For vendor-independent comparability check results, generic designations are necessary and will be specified in the following paragraphs. Basic check routines are individual check routines which refer to an individual feature (for example, the IR absorption). Composite check routines are defined as logical combinations of basic check routines. Thus, an enhanced characteristic can be checked with respect to several features, such as IR absorption and visibility in the VI. 

For the check routines, the following abbreviated definitions are used: 

## **(XX, YY, ZZ)** 

**XX** specifies the light source of the record on which the check routine is performed: 

- **IR** - infrared light 

- **UV** - ultraviolet light 

- **VI** - visible (white) light 

**YY** specifies the optical property of the characteristic: 

- **AB** - absorbent 

- **BR** - bright 

- **FR** - spatial frequency property 

- **LU** - luminescent 

- **TL** - translucent 

- **TR** - transparent 

**ZZ** specifies the characteristic feature of or the position in the document[2] : 

- **FI** - fibres 

- **FU** - full (complete) data page 

- **IS** - printed feature, which already exists on the substrate (Ink static) 

- **MR** - area of the machine readable zone (MRZ) 

- **OM** - overprinted MRZ 

- **CA** - Card Access Number (CAN) 

- **PD** - personalized "dynamic" perforation 

- **PS** - perforation which shows "static" content 

- **PH** - area of the photo 

- **SP** - area of the secondary photo 

- **OP** - overprinted photo 

- **TH** - security thread

## 5.7.2.3 Catalog for spectrally selective checks 

Further information on the spectrally selective checks might be required by the operator for evaluation pur poses and to update the underlying database to assure consistent and high quality authentication results over time. This information is the same for all documents of a specific document model, for example, textual ex planations on the check routines, the image section from the reference database etc. 

The vendor SHALL supply a catalog in machine readable form according to the defined Extensible Markup Language (XML) schema of this Technical Guideline which summarizes all necessary information on the spec trally selective verification checks. Due to the format, the catalog can be integrated into the evaluation of the results. 

In addition, the catalog SHALL include the following information on each generic check routine of a docu ment model: 

- UUID of the check routine: This value specifies the unique id for the check. 

- Generic check identifier: This attribute contains the generic check routine specification name, e. g. **(UV, BR, VZ)** . 

- Proprietary check: This attribute contains a vendor-specific name of the spectrally selective check routine (e. g. according to the entry in the check database). 

- Description: This attribute contains a textual description of the check routine performed and, in particular, an explanation of the differences in the checks with multiple applications of one and the same generic specification. 

- Maximal range: This attribute contains the upper limit of the range of values. 

- Minimal range: This attribute contains the lower limit of the range of values. 

- Threshold: This attribute contains the threshold configured for the decision for the spectrally selective ve rification. 

- Limits: 

   - Bounding rectangle: The bounding rectangle for the checking area if it is not a region. 

   - Region: This element contains the description of an alternative geometric check region if a bounding rectangle is not applicable. The type description is freely definable by the vendor, the definition SHALL be disclosed to the operator. 

- Reference area: This element contains the image section of the reference image region checked against the corresponding database. 

For composite generic check routines, the function of which the decision is taken (so-called decision function) SHALL be specified. Any proprietary decision function SHALL be described by the vendor and disclosed to the operator. If it is not possible to describe the decision function technically, its functioning SHALL described to be comprehensible. 

The catalog SHALL list all test configurations. The test configurations assort the checks into check groups and include decision functions for the given document models. The checks for a specific model SHALL be conducted according to the configuration given in the catalog. For each configuration a unique identifier (UUID according to [RFC4122]) SHALL be assigned. Multiple configurations can exist for a given document model. The choice of a configuration is vendor specific.

## 5.7.3.10 Spectrally selective verification 

Most MRTDs can be checked regarding their authenticity by verifying their spectrally selective security fea tures. The specific spectrally selective check routines being performed depend on the document model. One exception is (IR, AB, MR) (e. a. B900), which can be parametrized independently from a specific document model. With certain restrictions on accuracy, (UV, BR, FU) can also be performed without selecting a specific document model. 

Please refer to [BSI TR-03135-2] for mandatory checks. 

## 5.7.3.10.1 Optical document model database 

Because checks are document dependent, using a dedicated database tailored to the specific check is RECOM MENDED in all cases. This database SHALL be updated regularly in order to reduce false acceptance and re jection rates. It is RECOMMENDED to specify and maintain the contents of the database together with the operator; in most cases, this includes: 

- Definition of model identifiers in order to differentiate the document models. 

- Definition of search areas and their contents as well as the checks based on them including thresholds and ranges of values. 

- Subsequent extension, correction and readjustment of the specified checks in order to be able to take into account any experience gained with respect to the variances in the features of authentic documents to be checked (e. g. regarding aging effects, traces of usage, variability in the production process). 

The specified checks, as well as their associated thresholds, proprietary decision functions, etc. SHALL be do cumented and disclosed by the vendor. 

## 5.7.3.10.2 Hierarchical organization of checks 

There are three levels in the hierarchy of spectrally selective checks: 

- Basic and composite checks, 

- group checks, and 

- the final spectrally selective verification result.

## 5.8.10 Integrity of chip characteristics 

The previous sections described the security mechanisms of an eMRTD as described in [ICAO9303] and [BSI TR-03110]. Protocols such as PACE or Chip Authentication and Terminal Authentication, but also Passive Authentication, significantly increase the security of the chip and the whole document. 

Normally, the inspection system reads the information provided by the eMRTD chip and then decides which protocols and algorithms to use (see figure Figure 5.3 or section Section 5.8.8). For example, the inspection system reads `EF.CardAccess` and then decides which of the offered PACE algorithms to perform. In this way, the inspection system trusts the chip in the eMRTD. If the chip is manipulated in such a way that it pretends to be a simple chip without any electronic security features or a chip with reduced security features (e.g. BAC instead of PACE), the inspection routines at border control will be bypassed. In this case, the inspection system could trust the chip and run no (or reduced) security protocols. This type of attack could be prevented by checking for the presence of the `EF.SOD` with semantically complete content. In general, however, it would be helpful to know which algorithms and protocols can be expected from an eMRTD. 

To avoid such attacks, an additional reference database of chip information is helpful. Such a database is al ready widely used for optical security checks. With such a database, a chip can be checked for plausibility at the beginning of the electronic reading process. This database contains a 'fingerprint' of the chip with basic information about the chip. The inspection system can compare the expected data (database) with the data

## 5.8.11 Digital Travel Credentials (DTC) 

Designed to support seamless travel at the airport, a DTC is intended to serve as a secure and globally inter operable digital representation of a physical eMRTD. A key feature of the DTC is that it allows border authori ties to verify a digital representation of the eMRTD data prior to the traveler's arrival, confirming the integrity and authenticity of the data. 

There are different types of DTC that consist of two distinct components. These components are the eMRTD DTC Virtual Component (DTC-VC) specified in [ICAODTC-VC] and the eMRTD DTC Physical Component (DTC-PC) specified in [ICAODTC-PC]. 

The DTC-VC is a digital representation of the eMRTD data that is cryptographically linked to the issuing aut hority (i.e., digitally signed by the issuer). This enables verifiers to check the digital signature to confirm the authenticity of the credentials and that the data has not been altered after issuance. The DTC-VC is a file that can be stored on any medium. It does not have any inherent access protection on its contents. 

The DTC-PC is a kind of carrier for the DTC-VC and serves as a unique physical authenticator. Similar to the relationship between the eMRTD book and its embedded chip, the DTC-VC is cryptographically linked to its DTC-PC via digital signatures. This allows verifiers to confirm the association of a DTC-VC with its correspon ding DTC-PC to further authenticate the DTC. The can be created on any token that supports the DTC speci fications (smartphones, wearables, etc.). 

A DTC can be implemented in four different ways, each offering different options for issuers and verifiers. It is important to note that these four DTC types are not hierarchical, nor do they represent evolving DTC solutions. Hence, all DTC types use the same technical specifications for the DTC-VC.

## 5.8.11.1 Reading a DTC 

The process of reading a DTC depends on the type of the DTC. 

The DTC types, eMRTD-PC bound and PC bound are alternative representations of information contained in the electronic chip embedded in the eMRTD. For instance, the same cryptographic protocols and the same data groups (including some new ones) are used in the context of the DTC. Only the underlying transmissi on protocols may be different, i.e. besides NFC, there may be new protocols such as WiFi Aware or BLe. On the logical layer, however, the same cryptographic protocols and the corresponding checks can be used as described in Section 5.8.8.1. To put it another way, from a logging perspective, these two types of DTC can be handled similar to a common eMRTD. 

The DTC types, eMRTD bound and eMRTD bound extended, are virtual representations of the chip’s content. Therefore, the process at the border is different: 

1. The traveller derives a DTC-VC from their eMRTD. 

2. The traveller transmits the DTC-VC to the border control system. 

3. To verify that the DTC belongs to the traveller, a facial image of the traveller is captured during the border control process. 

4. A background system performs a 1:N search on the available facial images of all 

   - DTC-VC to find a match. 

5. If a DTC-VC is found where the contained facial image matches with one in the background system, this DTC-VC is transmitted to the border control station. 

6. PA is performed with the DTC-VC to assure the integrity of its data. 

7. The border control system requests the traveller to present his eMRTD to verify the DTC-VC. For this, PACE establishes a secure channel to the eMRTD and CA is executed to ensure the authenticity of the eMRTD. Alternatively, PACE-CAM (a combination of PACE and CA) can be executed. 

8. If all steps are successful, the border control system allows the traveller to pass. 

In any case it is important to note that in contrast to the data groups on a chip, a DTC-VC is a file that can be modified by third parties. Hence, to assure that no data is modified, it is necessary to perform PA with the DTC-VC, i.e. all checks specified described in Section 5.8.4 and Section 5.8.5 must be performed for the DTC-VC. This way, the integrity of the data can be verified. 

A DTC of type eMRTDbound extended with additional data stored in the virtual component, plays a special role in verification process. This is because all additional data in the virtual component must be signed by the issuing authority. Accordingly, during the border control process, this signature must also be checked to assure the integrity of the additional data.

## 5.12 Handling and interpretation of defects 

During production of MRTDs errors may occur, both in the optical/physical parts and in the electronic parts. This section defines a procedure in the event of defects that may be ignored for the final result. If a defect was detected there MAY be a hint provided to the operator as to this fact. 

## 5.12.1 Optical defects 

There are documents issued that do not comply to requirements specified in [ICAO9303]. In such cases a check will fail, although the document was officially issued by a state. If such defects can be identified it is RECOM MENDED to provide additional information about the optical defect to the operator, or to log such informa tion for the operational monitoring. 

## 5.12.1.1 Specimen 

There are specimen documents in the field that correspond to authentic original documents. Such documents usually contain all security-related features of a MRTD and could be successfully checked. Such documents contain specimen labels that help to identify them as a demonstration or fake document. If possible, such documents SHOULD be identified and marked as specimen. 

## 5.12.1.2 Country identifier 

E. g. visas are sometimes issued with an incorrect country naming scheme. For example, instead of D for Ger many some countries issue DEU, GER or DE. But there are also other examples for a wrong country encoding. If it is known that a wrong country code was used, a defect SHOULD be specified and can be corrected for a further check. 

## 5.12.1.3 MRZ format 

In some passports and visa stickers the MRZ-format does not comply to [ICAO9303]. Regarding the individual defect, the MRZ might be corrected. If it is not possible to do so, checks relating on a correct MRZ- format SHOULD be skipped for such documents. 

## 5.12.1.4 MRZ font 

In some passports and visa stickers, a non-OCR-B font was used to print the MRZ. If it is known that an issuing country uses a wrong font it is RECOMMENDED to discard any optical checks relating on the exact OCR-Bfont. In case a digitized MRZ is editable, the defect SHOULD be specified and can be corrected. 

## 5.12.1.5 MRZ check digit 

Some passports and visa stickers contain wrong MRZ check digit values, because the issuing state missed the algorithm or set a default value, regardless of the individual document holder's MRZ data. If it is known that the MRZ check digit is malformed and will fail, checks relating the MRZ check digit SHOULD be skipped or the digitized MRZ SHOULD be corrected if possible.

## 5.12.1.6 MRZ non-IR-readable

This technical guideline does not specify defects for the Electronic Identity Document (eID) application.

## 6 Logging scheme for operational monitoring 

## 6.1 Use cases 

This chapter specifies a logging scheme, which makes it possible to document all technical activities performed during an inspection process. Such a logging scheme SHALL be used to measure the quality of the inspection process across different systems, regardless of the used hard- or software. This allows the implementation of operational monitoring: 

- To optimize the process of machine assisted checks on eMRTDs, 

- To adapt to new circumstances, and 

- To ensure that reliability, quality, transparency and traceability is given.

## 6.3 Logging profiling 

Any profiling based on the requirements of this guideline SHOULD provide one or more dedicated logging configurations to indicate which elements are to be logged under which circumstances. 

The following elements SHALL be logged in any case (i.e. if they are present after the process has finished): 

- Transaction identifiers, 

- Component version information, 

- Timing information, 

- All check results, 

- Document data that is not related to a person, 

- Statistical data about users that is not related to persons. 

Logging of additional elements is application specific and needs to be defined by the system operator. Speci fying the exact requirements SHOULD therefore be conducted together with the responsible Data Protection Officer. 

Possible examples for use cases are: 

- logging of document information in the case of suspicion of document fraud for deferred analysis, 

- logging of document data forensic application.

## 6.4.8 Performance capabilities 

It is RECOMMENDED to minimize the total duration of the document inspection without reducing the quality of the result. Each inspection step SHOULD be executed as soon as the input data, which is mandatory for the step is available to the IS, for example, a digitized MRZ or CAN to access the electronic component of the document under inspection. By passing the MRZ/CAN data to the electronic check component of the IS at an early stage, the total time of the inspection could be reduced, since the electronic and optical check component can perform their checks simultaneously.
