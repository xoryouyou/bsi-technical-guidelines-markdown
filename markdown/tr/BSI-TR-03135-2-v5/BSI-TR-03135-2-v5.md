2 Introduction 

## 2 Introduction 

This document is a part of [BSI TR-03135]. [BSI TR-03135] specifies and describes necessary requirements for machine assisted document checks on Machine Readable Travel Documents (MRTDs) in Public Sector App lications. 

## 2.1 How to use this document 

1. Comply with the requirements for all document inspection systems in 4.1: Requirements for all inspec tion systems. 

2. Identify your application scenario in 3.1: Application Scenarios Catalogue. 

3. Comply with the requirements for your application scenario in 4.2: Requirements for Application Sce narios. 

## 2.2 Terminology 

## 2.2.1 Key Words 

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC2119]. 

## 2.2.2 Definitions 

## 2.2.2.1 Capability 

The ability to perform a specific task or action that is relevant for a document inspection process. 

## 2.2.2.2 Application Scenario 

A set of circumstances that describes where, how, when and/or with what objective a document inspection system is used.

## 3.1 Application Scenarios Catalogue 

The following subsections describe all application scenarios, which occur in German Public Sector Applicati ons. 

## 3.1.1 Application scenario - Stationary 

Stationary systems are systems which are permanently installed at border crossings, at police stations or at other localities with raised focus concerning security issues (e. a. government buildings, ministries, embassies or official meeting locations) as well as temporary systems in accordingly prepared sites (e.g. for major events such as sports or music events). 

## 3.1.2 Application scenario - Self Service 

Self Service systems are systems with which automated or semi-automated document and identity checks are performed (e. g. so-called eGates/Automated Border Control (ABC) systems, automated border control systems/gates). 

## 3.1.3 Application scenario - Partially mobile 

Partially mobile application scenarios usually take place at checkpoints, in patrol cars or vessels, but also in rail, air and shipping traffic environments. This includes, for example portable PC stations, which are the size of a notebook, or a tablet PC. These systems are often equipped with a swipe or full-page reader in order to be able to read the Machine Readable Zone (MRZ)/Card Access Number (CAN), but also with a Radio-Frequency Identification (RFID)-chip reading module. 

## 3.1.4 Application scenario - Fully mobile 

Fully mobile application scenarios will usually be performed in rail, air and shipping traffic as well as during general patrol duty. The systems are carried by the officer. The devices have the similar size and design as smartphones or tablet PCs. 

## 3.1.5 Application scenario - Kiosk 

Kiosk application scenarios usually take place at border crossing points (air- or sea-ports). These systems are unengaged and unmanaged pillar styled units that can be operated by the traveller. A traveller can pre-register and pre-process before crossing the border. These systems are equipped with a full-page document reader in order to be able fully read the MRTD. This also includes reading the RFID chip of an Electronic Machine Readable Travel Document (eMRTD). In addition, such a kiosk system can capture live images of the traveller and fingerprints. An interactive electronic registration prompt guides the traveller through the process. 

## 3.1.6 Application scenario - Asylum registration 

Asylum registration application scenarios take place when a human seeking asylum is registered.

## 4 Requirements 

This chapter details the requirements from [BSI TR-03135-1] which are relevant for German Public Sector Applications. 

## 4.1 Requirements for all inspection systems 

The generic requirements of an Inspection System (IS) SHALL fit the requirements regarding Chapter 4: Inspection System Requirements and Chapter 5: Authentication of MRTDs in [BSI TR-03135-1]. 

## 4.1.1 Requirements on the execution of all checks 

If any check is required to be performed in a specific application scenario and expected to be applicable to the identified document model, all partial checks of that check that are expected to be applicable to the identified document model SHALL be performed, unless stated otherwise. All checks SHALL be performed with the `runMode` set to `mandatory` , unless stated otherwise. 

## 4.1.2 Requirements for the retrieval of certificate lists 

There are two scenarios for retrieving a new list of the type Master List or Signer List. 

## 4.1.2.1 Manual Retrieval and/or Deployment 

If the list has to be retrieved and/or deployed manually, the administrator of the document inspection system SHALL retrieve and deploy the most recent list at least once every four calendar weeks. 

## 4.1.2.2 Automatic Retrieval and Deployment 

The RECOMMENDED implementation is described in [BSI TR-03135-1] section 5.6.1.1. 

If the list can be automatically retrieved and deployed by the document inspection system, it SHALL retrieve and deploy the most recent list at least once every three workdays. It is RECOMMENDED to check for updates daily and to deploy them immediately. 

## 4.1.3 Requirements on operational monitoring 

The document check system SHALL implement the logging schema according to [BSI TR-03135-1], Chap ter 6: Logging scheme for operational monitoring. 

This document defines the following levels of logging configurations: 

1. Basic logging profile 

2. Standard logging profile 

3. Standard logging profile with optical evaluation extensions 

4. Standard logging profile with electronic evaluation extensions 

5. Standard logging profile with digital seal evaluation extensions 

6. Full logging profile 

The document check system SHALL implement all defined logging configurations. Setting the actual logging configuration SHALL be configurable by the application. 

An extended data node is a data node that uses a type from the `bsi-tr-additionaldata` schema. The extended data nodes for a certain check are all extended data nodes that are part of the check. 

## 4.1.3.1 Basic logging profile 

Basic logging SHALL contain all non-personally identifiable information from a check, including all check results. All data items from the Extensible Markup Language (XML) schema SHALL be filled, with the exception of the set of extended data nodes.

## 4.1.3.2 Standard logging profile 

Standard logging SHALL contain all available information from Basic logging profile and SHALL provide ad ditional information on the specific **failed** and **undetermined** check(s). 

For electronic check errors, the optical document data, i.e. all extended data nodes from `dco:ProcessInforma tion` and `dco:ComponentInformation` , SHALL be included to allow for cross-comparison of optical and electro nic document data. 

Depending on the type of error, the relevant sets of extended data nodes detailing the error SHALL be present in the log. Note that extended data nodes are not present if the corresponding check was aborted. If the inte grity check of a data group failed, then the extended data nodes of the optical check SHALL also be included. 

## 4.1.3.3 Standard logging profile with optical evaluation extensions 

Standard logging with optical evaluation extensions SHALL contain all information from Standard logging and SHALL contain all extended data nodes for the optical check regardless of the optical check result. Addi tionally, it SHALL contain all extended data nodes for the combined check and the cross document check that relate to the target of the evaluation. 

## 4.1.3.4 Standard logging profile with electronic evaluation extensions 

Standard logging with electronic evaluation extensions SHALL contain all information from Standard logging and SHALL contain all extended data nodes for the electronic check regardless of the electronic check result. Additionally, it SHALL contain all extended data nodes for the combined check and the cross document check that relate to the target of the evaluation. 

## 4.1.3.5 Standard logging profile with digital seal evaluation extensions 

Standard logging with digital seal evaluation extensions SHALL contain all information from Standard logging and SHALL contain all extended data nodes for the digital seal check regardless of the digital seal check result. Additionally, it SHALL contain all extended data nodes for the combined check and the cross document check that relate to the target of the evaluation. 

## 4.1.3.6 Full logging profile 

Full logging SHALL contain all available information including all extended nodes, regardless of the check results. 

## 4.1.4 Requirements for data transmission 

The IS SHALL implement the transmission and log specification according to [BSI TR-03135-1], Chapter 6: Logging scheme for operational monitoring for Application scenario - Stationary, Application scenario - Self Service, Application scenario - Kiosk and Application scenario - Asylum registration and it is RECOMMEN DED for the ISto to implement it for the Application scenario - Partially mobile and Application scenario - Fully mobile application scenarios. Logging data SHOULD be temporarily kept local, if transmission fails and retransmitted if the connection is available, possibility to manually transfer logs is RECOMMENDED. 

## 4.1.5 Requirements on transactional logging 

The logging schema defined in this Technical Guideline can be used for the sole purpose of document inspec tion (stand-alone variant) but also in the wider context of identity management (payload variant) which also consists of biometrics and process management, among other things. 

For the stand-alone variant, the logging schema provides a transaction node below which all other checks are grouped. The transaction can be used to log messages in the scope of document inspection. In addition to checks of individual documents, checks between documents (cross-document checks) can also be logged. 

One example of the payload variant is the logging in [BSI TR-03156]. When using this logging in identity ma nagement, no transaction node from the document check is used. Instead, the checks are transported via the so called `psidmlog` . In this case, the log is a container for the document inspection logs.

## 4.4 Requirements for Checks 

The following sections describe requirements for checks. If additional checks are supported, their execution is RECOMMENDED, but SHALL be decided by the operator. Any checks that are performed SHALL be repre sented by the respective elements in the logging schema according to [BSI TR-03135-1], Chapter 6: Logging scheme for operational monitoring. 

## 4.4.1 Requirements for Check - Document 3.3.1 

The requirements for this check are as follows: 

- The false negative rate of the overall result of the document checking process per country SHOULD not exceed 2% for correctly placed, captured and identified documents. 

- handling of defects as specified in [BSI TR-03135-1], Section 5.12: Handling and interpretation of defects 

## 4.4.2 Requirements for Check - Optical 3.3.2 

The requirements for this check are as follows: 

The inspection system SHALL offer a configuration option that changes the `runMode` of the spectrally selective checks to `conditionallyIgnored` under certain conditions. To enable this feature, the inspection system SHALL support a whitelist of countries. This whitelist SHALL be configurable by the operator of the inspection system. 

The change of the `runMode` of the spectrally selective checks SHALL only be applied if the following conditions are met: 

- The document under inspection was issued by a country that is included in the whitelist. 

- The 3.3.15: Check - Electronic was successful. 

## 4.4.3 Requirements for Check - Spectrally Selective Verification 3.3.14 

The requirements for this check are as follows: 

Partial checks SHALL be performed according to the identified document model. The vendor and the operator SHALL come to an agreement on which partial checks SHALL use which `runMode` .
